The Ignosis engineering team practises a plan-first, ship-small, code-review-heavy variant of agile delivery. Each unit of work begins in Jira and is decomposed into a short Markdown plan stored in the repository under . The plan answers four questions: what is the user-visible behaviour, what entities or tables change, what services or controllers are added or modified, and what tests need to be written. The plan is reviewed by the engineering lead before any code is written. Once accepted, a branch is created from following the Gitflow naming convention -- typically or -- and the implementation begins. Conventional commits are enforced. Each commit is prefixed with a type ( , , , , , ) and a scope. Pull requests are squashed into a single commit on the receiving branch only when the history is messy; otherwise the rebased history is preserved. The Ignosis main branch ( ) is treated as the release branch. Tags follow semantic versioning. The current version of the orchestrator at the time of writing is 1.5.1. Tests live next to the code they exercise. The repository is configured with JUnit 5 and Mockito on the Java side and Vitest on the TypeScript side. Integration tests run against a Testcontainers-managed PostgreSQL instance, an embedded H2 for the lighter repository tests, and a stubbed Bolna service over Spring's . The pipeline aborts when SonarQube reports either a new bug, a new code smell above the medium severity threshold or a new vulnerability of any severity. Multi-tenancy is implemented via host-based routing. A small servlet filter, , inspects the incoming request's header and looks up the corresponding tenant identifier in a configuration map. The tenant identifier is set on a held by the class and is read by every downstream layer that needs to scope its work to a tenant. The thread-local is dangerous in the presence of asynchronous code, because the Spring default executor does not propagate request-scoped state. To handle this the team introduced , a small wrapper around that captures the tenant identifier on the calling thread and re-establishes it on the worker thread. All asynchronous code in the codebase is expected to go through this wrapper -- raw is forbidden -- and a Sonar rule is configured to detect violations. Authentication and authorisation are layered. Five separate beans run in priority order and each one matches a disjoint subset of the URL space. The most important chains are: The OAuth 2 Resource Server chain for dashboard requests. The JWT issuer is the Keycloak realm of the resolved tenant. An API-key chain for tenant-issued credentials, used by the lender-side automation that posts allocation files to our REST endpoints. A webhook chain that authenticates Bolna's call-status webhook posts using a shared secret in a custom header. A second API-key chain for AA partner callbacks. A legacy chain for collection partner APIs that pre-dates the OAuth integration. The security configuration is consolidated in , which is a single Spring class that declares all five chains. A campaign is the unit of bulk work in the platform. A campaign manager creates a campaign, uploads a CSV of customer rows, optionally previews and corrects the data, and submits the campaign for execution. The platform then drives the campaign through the workflow engine until every case in the campaign reaches a terminal state. The campaign creation form collects the campaign name, an optional description, a priority (low / medium / high), a target collection amount, an assignment rule (round-robin, weighted, manual) and a calling window (active hours during which AI calls are permitted). The CSV upload field accepts files up to fifty megabytes; on the client side the file is validated for extension, size and required columns before being submitted to the backend. The backend endpoint /campaigns accepts the form fields and the file as multipart data. The parses the CSV with the OpenCSV library, validates each row (phone present, due amount numeric and positive, name present, account number valid format), and emits a preview response that contains the total row count, the count of valid rows, the count of invalid rows and, for each invalid row, the row number and the reason. The campaign manager reviews the preview, fixes obvious issues if needed and submits the campaign for execution. On final submission, the backend persists a entity along with one per valid row. Each carries the customer phone, name, due amount and an initial state of . The campaign goes into the or state depending on whether a future start time was set. A first-pass scheduler picks up the campaign on its next tick and begins enqueueing jobs. Job execution inside the orchestrator is built around a database-backed job queue. A row carries a payload (a JSON blob), a job type (one of about a dozen enum values), a state ( , , , , ), a scheduled-for timestamp and a tenant identifier. A scheduled service polls for jobs whose scheduled-for time is in the past, takes a row-level lock with a 180-second TTL via the table, looks up the executor for the job type, and runs it. The advantage of a database queue, compared with a Redis queue, is that the entire state of every in-flight job is visible to ordinary SQL queries. Operationally this is enormously valuable: when something is wrong with a campaign at 3~AM, the on-call engineer can query the table directly to see exactly where each case is stuck. The downside is throughput -- the queue cannot handle the millions-per-second message volumes that Redis-based queues comfortably handle -- but at the campaign volumes the platform sees in production this is not a real constraint. A separate Redis-backed priority queue is used for the small subset of jobs where order-of-arrival latency is the dominant concern, in particular the auto-loading of the next case when an agent submits a disposition. The speed dialer is the part of the platform that maximises an agent's throughput. When an agent is working on a campaign, the dashboard shows the active case in a panel; the agent has the customer's phone dialled, talks to the customer, fills out a small disposition form (Promise to Pay, Wrong Number, Customer Disputes the Amount, etc.) and submits. The moment the disposition lands at the backend, the campaign workflow engine evaluates the next node for the case, the case enters a terminal-for-this-agent state, and the speed dialer fetches the next pending case in the campaign queue. The new case is pushed to the dashboard via Server-Sent Events. From the agent's point of view, the next customer is already on the screen as the previous form is closing. AI voice calling is the corollary capability that lets the platform continue working after the agent's day is over. For each campaign, a fraction of the cases are routed to the AI track rather than to a human agent. The AI track is driven by a different executor, , that picks the next AI-eligible case, fetches the tenant-configured Bolna agent ID, fetches the next phone-number-from-pool through the , builds the Bolna make-call payload from the case context and calls Bolna's REST API. Bolna places the call through Exotel, conducts the conversation under a tenant-specific prompt, and on call completion posts a webhook to our endpoint. The webhook payload contains the call disposition, the duration, a structured extraction of variables (promise-to-pay date, dispute reason, callback request), a recording URL and the latency breakdown. The parses the payload, persists the outcome, cancels any in-flight status-poll job for the same call, emits Prometheus metrics and triggers the next node in the workflow.
