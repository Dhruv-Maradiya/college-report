\chapter{Software Design}
\label{Chapter 4}

The previous chapter described the platform from the perspective of the features that were built. This chapter steps back and describes the same platform at the design level: the goals the design was tested against, the components into which the system decomposes, the data model that ties those components together, the principal sequence flow and the security model.

\section{Design Goals}

The platform was designed against a small, prioritised set of goals. Tenant isolation is at the top of the list because a leak across tenants is unrecoverable in a regulated environment. Configurable collection policy sits above cost-aware channels because a tenant whose policy is hard-coded into the orchestrator will eventually require a code change just to be onboarded. The remaining goals are operational: auditability, observability and graceful degradation. The full list is summarised in Table~\ref{tab:design-goals}.

\textbf{Goal} & \textbf{Design implication} \\

\section{Component Decomposition}

The platform decomposes into seven major components, each owning a well-defined slice of the system surface. Inter-component communication is exclusively over HTTP with API-key or JWT authentication; within a component, the layering is conventional (controller, service, repository on the Spring Boot side; page, hook, service on the React side) and is enforced by review rather than by package boundaries. \section{Data Model}

The data model is a normalised relational schema in PostgreSQL, with denormalised projections cached in Solr for search and in ClickHouse for analytics. The most important relationship in this model is the one between \texttt{Case} and \texttt{UserAllocation}: the case is a stable handle on the customer's relationship with the lender, while the allocation is the cycle-specific projection that the workflow engine drives. Splitting the two keeps the case timeline append-only across cycles and lets a case carry its history forward even when its workflow position is reset at the start of a new cycle. The append-only \texttt{CaseEvent} table is the second important design choice: every action the platform takes against a case appends a row, so queries that show the timeline read from this table directly while queries that need the current state read materialised columns on \texttt{Case} and \texttt{UserAllocation}. This separation keeps the live tables small and the timeline easy to audit.

\section{Principal Flow: AI Voice Call}

The AI voice call is the most architecturally instructive flow because it crosses every major component and exercises the workflow engine on both the outbound and the inbound side. The orchestrator's scheduler reaches an AI-call node for a case, schedules a call-initiate job, and a defensive status-poll job five minutes later. The job executor pulls the next from-number, builds the Bolna payload and POSTs it; Bolna conducts the call through Exotel and POSTs a terminal webhook at completion. The webhook processor persists the disposition, cancels the poll job, emits Prometheus metrics, and the engine evaluates the outgoing transitions of the current node so the workflow advances on the same request. Two non-obvious points: the defensive poll job exists because the Bolna webhook is best-effort and a polling fallback ensures the case is never indefinitely parked, and the cancellation is implemented as a soft cancel (the poll job runs, observes the case already terminated and exits) which is more robust against database eventual consistency than a hard cancel would be.

\section{Security Design}

The security design rests on independent layers so that a breach of one does not compromise the layers below. Users authenticate against Keycloak with short-lived per-realm-signed JWTs. Every API call resolves the tenant identifier from the URL prefix and rejects any JWT whose realm does not match, and a thread-local tenant context propagates the tenant identity through every downstream call including across asynchronous boundaries. Role-based access control is enforced both at the controller layer (Spring Security) and at the dashboard layer; every JPA query is scoped to the tenant, every Solr query is routed to the tenant's core, every ClickHouse query carries the tenant tag in its filter, with cross-tenant queries forbidden at the repository layer. Inbound webhooks are authenticated with an HMAC over the body or with a monthly-rotated API key, with the secret in AWS Secrets Manager. A separate set of compliance controls -- call-frequency guards, do-not-call honour periods, PII access logging, recording retention -- is enforced uniformly across all tenants regardless of individual configuration.
