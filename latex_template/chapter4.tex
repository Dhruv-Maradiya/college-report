\chapter{Software Design}
\label{Chapter 4}

The previous chapter described the platform from the perspective of the features that were built. This chapter steps back and describes the same platform at the design level: the goals the design was tested against, the components into which the system decomposes, the data model that ties those components together, the principal sequence flow and the security model.

\section{Design Goals}

The platform was designed against a small, prioritised set of goals. Tenant isolation is at the top of the list because a leak across tenants is unrecoverable in a regulated environment. Configurable collection policy sits above cost-aware channels because a tenant whose policy is hard-coded into the orchestrator will eventually require a code change just to be onboarded. The remaining goals are operational: auditability, observability and graceful degradation. The full list is summarised in Table~\ref{tab:design-goals}.

\begin{table}[H]
\centering
\caption{Prioritised design goals.}
\label{tab:design-goals}
\begin{tabularx}{\textwidth}{l X}
\toprule
\textbf{Goal} & \textbf{Design implication} \\
\midrule
Tenant isolation by default & Per-tenant identity realm, per-tenant search partition, tenant-scoped database queries, thread-local tenant context propagated across asynchronous boundaries. \\
Configurable collection policy & Workflow stored as data (nodes plus boolean transitions), not as code. Tenant edits do not require a deployment. \\
Multi-channel orchestration & Channels are workflow action types. Adding a new channel reduces to adding a new node type, not rewriting the orchestrator. \\
Auditability & Every state transition writes a row to the case timeline; every outbound action carries an idempotency key. \\
Graceful degradation & Database-backed job queue, per-job retry policy with exponential backoff, dead-letter handling for permanent failures. \\
Cost-aware channels & SIM-based WhatsApp and SMS rather than vendor-priced APIs; AI calls only when the workflow asks for them. \\

\section{Data Model}

The data model is a normalised relational schema, with denormalised projections cached in a search index for queries and in an analytics event store for reporting. The most important relationship is the one between the case and its per-cycle allocation: the case is a stable handle on the customer's relationship with the lender, while the allocation is the cycle-specific projection that the workflow engine drives. Splitting the two keeps the case timeline append-only across cycles and lets a case carry its history forward even when its workflow position is reset at the start of a new cycle. The append-only case-event table is the second important design choice: every action the platform takes against a case appends a row, so queries that show the timeline read from this table directly while queries that need the current state read materialised columns on the case and the allocation. This separation keeps the live tables small and the timeline easy to audit.

\section{Principal Flow: AI Voice Call}

The AI voice call is the most architecturally instructive flow because it crosses every major component and exercises the workflow engine on both the outbound and the inbound side. The orchestrator's scheduler reaches an AI-call node for a case, schedules a call-initiate job, and a defensive status-poll job five minutes later. The job executor pulls the next from-number, builds the request and hands it to the internal voice AI platform; the platform conducts the call through the telephony gateway and returns a terminal callback at completion. The callback processor persists the disposition, cancels the poll job, emits metrics, and the engine evaluates the outgoing transitions of the current node so the workflow advances on the same request. Two non-obvious points: the defensive poll job exists because the callback is best-effort and a polling fallback ensures the case is never indefinitely parked, and the cancellation is implemented as a soft cancel (the poll job runs, observes the case already terminated and exits) which is more robust against database eventual consistency than a hard cancel would be.

\section{Security Design}

The security design rests on independent layers so that a breach of one does not compromise the layers below. Users authenticate against the identity layer with short-lived signed tokens. Every API call resolves the tenant identifier from the URL prefix and rejects any token whose realm does not match, and a thread-local tenant context propagates the tenant identity through every downstream call including across asynchronous boundaries. Role-based access control is enforced both on the backend and on the dashboard; every database query is scoped to the tenant, every search query is routed to the tenant's partition, every analytics query carries the tenant tag in its filter, with cross-tenant queries forbidden at the data-access layer. Inbound callbacks are authenticated with a signed body digest or with a monthly-rotated API key, with the secret kept in the cloud provider's secrets manager. A separate set of compliance controls -- call-frequency guards, do-not-call honour periods, PII access logging, recording retention -- is enforced uniformly across all tenants regardless of individual configuration.
